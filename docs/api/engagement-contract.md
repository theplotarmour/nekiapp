# Notifications, connection tickets and saved methods

**Status:** P0 review draft, 2026-09-12. Adds the final six JSON HTTP operations, bringing coverage to 315 of 324 inventory operations. Nine public-web/WebSocket operations remain untyped in the [manifest](openapi-coverage.json). This does not close OpenAPI review or P0, and no runtime exists for these operations.

Source: [contract_engagement.py](../../tools/contract_engagement.py), [notification/realtime recovery rules](../state-machines/events-and-recovery.md), D5, FR-14 and AP-02. Run the [shared reproduction commands](identity-contract.md).

Notification pages expose safe owner content, a typed destination reference, occurrence ID, inbox version and snapshot ID. The server must authorize the subject before composing content; a previously authorized occurrence is not perpetual access. URLs, pickup addresses and private media are excluded from the shape. The five preference category tokens follow the existing identity contract; template-to-category reconciliation with FR-14 remains review work.

Mark-read commands select explicit owned IDs or a previously issued inbox snapshot. A snapshot operation must not mark concurrent later arrivals read. Cursor, snapshot, occurrence and inbox-version semantics require database tests, including duplicate delivery, new reschedules, unknown IDs and concurrency. Read status is independent of sent/push/quiet-hour status.

Connection tickets specify bounded explicit channels and a current device. The server derives user/session, validates device ownership, origin where applicable, assignment and source access, and issues a short-lived cryptographically random single-use token. Ticket output is sensitive and must not be logged. No wildcard or caller-selected user channel is allowed. Issuance and consumption need atomic binding to the current session and authorized channel set; every subscription and emission still needs revocation checks. The proposed `neki.realtime.v1` subprotocol and `/ws` handshake are not implemented; message frames, reconnect and close semantics are the next transport specification.

Saved methods expose only provider-supported masked card metadata with a local owner-bound ID. Availability is explicit, and unavailable responses contain no methods or pagination. The schema's illustrative card does not prove account/SDK saved-card capability. Provider metadata may describe tokenized-card digits and must use accurate display copy after compatibility verification. Raw PAN, CVC and provider token credentials must never enter the response or NEKI storage.

Removal requires step-up and the method version. It disables local reuse, queues provider removal and returns a pending operation without claiming provider confirmation. Uncertain results retain reconciliation work and never erase payment history. The provider vault/token mapping, consent, expiry handling and exact supported payment-method types remain D5/provider research obligations; this contract does not introduce a NEKI wallet or saved-method creation endpoint.

Validation passes 315 operations and 3,592 attached examples, rejecting 257 negative schema cases and five query cases. The 13 new negative cases cover private notification content, arbitrary destinations, broad read commands, wildcard/impersonated channels, reusable tickets, credential/card leakage and premature provider removal. No SMS/push, browser origin, ticket race, provider vault or notification database behavior has run. Strict completeness fails with nine transports untyped; all policy, research and P0 approval gates remain open.
