# Checkout, payment, refund and payout transitions

**Status:** P0 review draft, NK-DOC-3.02. [Shared command rules](README.md) and [money invariants](money-invariants.md) apply to every row. Existing sources: TDD §6.2/6.3/10; data model §4.5; D2/D3/D5. New orchestration/recovery states and all new event/error names are proposals pending schema/API reconciliation.

Every command requires current version and scoped authorization, atomic history/audit/outbox and idempotency. Provider observations use an authenticated inbox/reconciliation service principal and deduplicate provider identities; they are not rejected merely because the client or mission has advanced. A stale observation cannot regress financial facts. Local `EXPIRED` is not provider payment expiry. Any event can be delayed or duplicated.

## Checkout orchestration (new local aggregate)

| ID | Command: from → to | Actor | Guards/evidence | Atomic effects; proposed event | Copy; notification | Errors / dependencies |
|---|---|---|---|---|---|---|
| P01 | Create intent: absent → INTENT_RECORDED | Contributor | Current eligible money need/org; server amount/currency and disclosed fee snapshot, online request; sufficient need reservation | Contribution PENDING_PAYMENT + checkout intent/receipt/request hash + reservation; `CheckoutIntentRecorded.v1` | “Preparing secure payment”; owner status | `NEED_CLOSED`, `AMOUNT_INVALID`; FD-04 |
| P02 | Dispatch order request: INTENT_RECORDED → CREATE_REQUESTED | Checkout worker | Current intent/version, stable receipt and provider request | Durable invocation marker; `CheckoutOrderRequested.v1`; perform external request after commit | “Preparing secure payment”; no push | `CHECKOUT_NOT_ACTIVE`; RP-02 |
| P03 | Attach response: CREATE_REQUESTED / CREATE_UNCERTAIN → ORDER_READY | Checkout/reconciliation worker | Provider order matches receipt/account/environment/amount/currency; locally current authorization | Attach unique provider order; `CheckoutOrderReady.v1` | Offer checkout only if intent still active; owner status | `PROVIDER_ORDER_MISMATCH`; RP-01/02 |
| P04 | Lost response: CREATE_REQUESTED → CREATE_UNCERTAIN | Worker/watchdog | Timeout or interrupted invocation without conclusive outcome | Durable reconciliation work; retain uncertainty; `CheckoutOrderUncertain.v1` | “We're checking your payment setup”; owner + ops if aged | No fresh order retry; RP-02 |
| P05 | Proven no order: CREATE_REQUESTED / CREATE_UNCERTAIN → CREATE_FAILED | Reconciliation worker | Conclusive provider rejection/non-creation evidence; empty receipt query alone insufficient | Record evidence; release only eligible unused reservation; `CheckoutOrderFailed.v1` | “Payment could not be started”; owner retry/support per policy | `PROVIDER_OUTCOME_UNKNOWN`; FD-04 |
| P06 | Stop local checkout: INTENT_RECORDED / CREATE_REQUESTED / CREATE_UNCERTAIN / ORDER_READY → LOCALLY_CLOSED | Contributor or expiry service | Cancel/expiry reason and current local version | Disable new checkout presentation; release local capacity per policy; keep uncertain invocation/provider reconciliation alive; `CheckoutClosed.v1` | “Checkout closed; payment status checked separately”; owner | `CHECKOUT_STATE_CONFLICT`; FD-04 |
| P07 | Resolve closed order: LOCALLY_CLOSED → LOCALLY_CLOSED | Reconciliation worker | Late response/lookup matches original request | Attach order/evidence, advance version, route payment observations to P08–P11; never reopen checkout automatically; `ClosedCheckoutOrderResolved.v1` | Owner pending/recovery projection; ops if unresolved | `PROVIDER_ORDER_MISMATCH` |

P02's persisted invocation can outlive a cancellation. Before calling the provider recheck local state, but do not assume that check removes the external-call race. P06 cannot cancel a provider side effect by rolling back local state. Retry is a new local attempt only after FD-04/RP-01 criteria and all older uncertainties are resolved; duplicate UI taps replay the original command.

## Provider observations and capture allocation

| ID | Command / prior facts | Actor | Guards/evidence | Atomic effects; proposed event | Copy; notification | Errors / dependencies |
|---|---|---|---|---|---|---|
| P08 | Observe authorized/failed/payment entity | Verified inbox or server reconciliation | Raw signature or authenticated fetch; known account/environment/order identity and expected currency/amount | Append observation + provider entity projection, no capture credit; `PaymentObserved.v1` | “Confirming payment” or specific verified attempt failure; owner | Unknown identities quarantined/reconciled, not silently discarded |
| P09 | Observe captured, no existing capture fact | Same | Verified captured evidence, exact account/payment/order linkage and amount; accept evidence even if order linkage recovery pending | Unique capture fact; unresolved links go to recovery; `PaymentCaptured.v1` | “Payment confirmed” only for matched owner; no impact issued | `PAYMENT_LINKAGE_UNRESOLVED`; G11 |
| P10 | Allocate matched capture, no prior accepted contribution allocation | Allocation service | Under shared locks: intent/need/org still eligible, capacity and amount policy satisfied, one accepted contribution allocation | Create allocation credit; contribution CONFIRMED, counters once, receipt issuance intent; `ContributionConfirmed.v1` | “Contribution confirmed”; owner + org scoped feed | `ALLOCATION_NOT_ELIGIBLE`; FD-01 |
| P11 | Capture cannot be allocated, including duplicate successful attempt | Recovery service | Captured fact and mismatch/closed-need/extra-capture reason | Durable recovery liability and case; no mission credit; `PaymentRecoveryRequired.v1` | “Payment received; resolution in progress”; owner + Finance queue | FD-01/FD-02 |
| P12 | Observe provider settlement/adjustment | Reconciliation service | Provider settlement report and matched fact references | Settlement cash facts/reconciliation only; `GatewaySettlementRecorded.v1` | Finance status only; never “Received by organization” | `SETTLEMENT_MISMATCH`; G10/G16 |

Repeated capture/order-paid events no-op on existing fact, preserving processing receipts. A late failure/authorization does not delete capture or credit. Contribution payment failure is not final if any other attempt is unresolved. A partially refunded capture stays a historical capture, not an erased payment.

## Refund intent (new explicit state contract)

| ID | Command: from → to | Actor | Guards/evidence | Atomic effects; proposed event | Copy; notification | Errors / dependencies |
|---|---|---|---|---|---|---|
| R01 | Request: absent → REQUESTED | Scoped ops/Finance or policy service | Authorized reason, captured payment, requested amount; total processed + active requested refunds <= capture; locked source funds | Persist refund intent, reserve customer-refundable amount and approved principal/platform funds; `RefundRequested.v1` | “Refund requested”; owner + Finance | `REFUND_AMOUNT_UNAVAILABLE`, `RECOVERY_FUNDING_REQUIRED`; FD-02 |
| R02 | Authorize: REQUESTED → APPROVED | Scoped Finance | Eligibility/funding/approval policy, immutable body and source | Approve exact amount/key/body; `RefundApproved.v1` | “Refund approved”; owner status | `REFUND_POLICY_DENIED`; FD-02/03 |
| R03 | Send: APPROVED → SUBMITTED | Refund worker | Stable persisted provider idempotency key/body; current approval | Invocation marker then external request; `RefundSubmitted.v1` | “Refund processing”; owner | RP-05 |
| R04 | Response lost: SUBMITTED → UNCERTAIN | Worker/watchdog | No conclusive provider outcome | Preserve all reservations, queue lookup/same-key retry; `RefundUncertain.v1` | “Refund processing”; ops aged queue | Never release on timeout |
| R05 | Provider pending: SUBMITTED / UNCERTAIN → PENDING | Verified inbox/reconciler | Matched provider refund/key/payment/amount | Attach refund identity and observation; `RefundPending.v1` | “Refund processing”; owner status | `REFUND_PROVIDER_MISMATCH` |
| R06 | Processed: SUBMITTED / UNCERTAIN / PENDING → PROCESSED | Verified inbox/reconciler | Authoritative processed evidence, exact amount/identity | Unique refund fact, consume reserved funds once, update refundable balance/projection; `RefundProcessed.v1` | “Refund processed” with provider reference, no guaranteed bank arrival date; owner | RP-05/FD-02 |
| R07 | Failed conclusively: SUBMITTED / UNCERTAIN / PENDING → FAILED | Verified inbox/reconciler | Authoritative failure with identity and evidence; no prior processed fact | Release only failed operation's reservation, retain failed history/case; `RefundFailed.v1` | “Refund needs attention”; owner + Finance | `REFUND_OUTCOME_UNKNOWN` |
| R08 | Cancel unsent request: REQUESTED / APPROVED → CANCELLED | Scoped Finance | No invocation/in-flight worker, reason and locked intent | Release reservation, preserve decision; `RefundCancelled.v1` | “Refund request cancelled” plus safe reason; owner | `REFUND_ALREADY_SUBMITTED` |

Out-of-order authoritative PROCESSED after a previously believed FAILED result still records the real refund fact and raises a reconciliation incident/funding exception; it must not be discarded to preserve a neat state graph. Subsequent refund attempts need a new reviewed intent only after conclusive failure; timeout retries keep the original provider key/body.

## Manual payout and transfer attempt

| ID | Command: from → to | Actor | Guards/evidence | Atomic effects; proposed event | Copy; notification | Errors / dependencies |
|---|---|---|---|---|---|---|
| Y01 | Draft: absent → DRAFT | Scoped Finance preparer | Same-org/INR allocation set, available balance and verified bank revision, exact positive total | Reserve all allocation amounts atomically; `PayoutDrafted.v1` | “Payout draft”; Finance queue | `ALLOCATION_CONFLICT`, `BANK_NOT_VERIFIED`; FD-03/06 |
| Y02 | Approve: DRAFT → APPROVED | Scoped Finance approver | Exact snapshot, cash/hold policy, step-up; >5000000 paise requires distinct approver under source rule | Freeze recipient/items/amount and approval; `PayoutApproved.v1` | “Payout approved”; Finance operator queue | `SECOND_APPROVER_REQUIRED`, `PAYOUT_HOLD`; FD-03 |
| Y03 | Begin transfer: APPROVED → APPROVED | Authorized Finance operator | No active transfer attempt; current approval and unchanged bank verification | Versioned transfer attempt STARTED before external bank action, reservations held; `PayoutTransferStarted.v1` | “Transfer awaiting confirmation”; operator | `TRANSFER_ALREADY_STARTED`, `BANK_REVISION_CHANGED` |
| Y04 | Mark uncertain: APPROVED → APPROVED | Operator/watchdog | Started attempt with missing bank outcome | Attempt UNCERTAIN + reconciliation case; retain funds; `PayoutTransferUncertain.v1` | “Transfer under reconciliation”; Finance queue | No new transfer or cancellation |
| Y05 | Record paid: APPROVED → PAID | Scoped Finance recorder | Bank confirmation/UTR/value date/recipient and exact amount matched to transfer attempt | Attempt confirmed; reserved → consumed, append evidence; `OrganizationPayoutRecorded.v1` | “Sent to organization”; org + Finance; received milestone only under evidenced policy | `TRANSFER_EVIDENCE_REQUIRED`, `TRANSFER_MISMATCH`; G16/FD-06 |
| Y06 | Reconcile: PAID → RECONCILED | Scoped Finance reconciler | Match bank report and allocation totals; resolution of variance | Append reconciliation; no balance release; `PayoutReconciled.v1` | “Payout reconciled”; Finance status | `PAYOUT_RECONCILIATION_MISMATCH` |
| Y07 | Cancel before transfer: DRAFT / APPROVED → CANCELLED | Scoped Finance | Reason; no started/uncertain/successful transfer, or conclusive no-transfer evidence | Release unconsumed reservation; `PayoutCancelled.v1` | “Payout cancelled”; Finance + org if previously notified | `TRANSFER_OUTCOME_UNRESOLVED` |
| Y08 | Record bank failure: APPROVED → APPROVED | Scoped Finance reconciler | Conclusive failed attempt evidence, not a timeout | Close attempt FAILED; reservations held for reviewed retry or Y07; `PayoutTransferFailed.v1` | “Transfer failed; action required”; Finance | `TRANSFER_OUTCOME_UNRESOLVED` |
| Y09 | Record returned transfer: PAID / RECONCILED → same | Scoped Finance reconciler | Unique bank return evidence linked to original transfer and approved accounting treatment | Append return fact; restore eligible allocation once; preserve original payment/reconciliation history; `PayoutReturned.v1` | “Payout returned; resolution pending”; org + Finance | `RETURN_EVIDENCE_REQUIRED`; FD-02/06 |

A cheque issued is not automatically bank-confirmed receipt; method-specific evidence must follow FD-03/06. Draft editing uses a separate versioned command that atomically replaces reservations; editing APPROVED amounts or recipient is forbidden. New payout after returned funds must be a new instruction referencing the return; never mutate old UTR/paid amount.
